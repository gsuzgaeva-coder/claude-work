# Проектирование и строительство учёта

Цель — рабочая система, а не идеальная схема. Формат выбирает логист: начни с того,
как логист видит учёт, и строй под это. Строим по одному источнику, каждый доводим
до сверки с первоисточником и только потом берём следующий. Если логист просит предложить
структуру с нуля — вариант в `knowledge/04_модель_учёта.md`; почему его правила важны —
`knowledge/03_…`.

## Этап 0. Разведка (первая сессия с логистом)

Прежде чем что-то создавать, выясните и запишите в `ЖУРНАЛ_ПРОЕКТА.md`:

0. **Как логист хочет работать.** Уже известно: Excel — уверенно; всё техническое
   делаешь ты. Выясни: в чём вести учёт (Google Таблица, Excel-файл, другое), есть ли
   наброски или своя таблица, что было удобно и неудобно в прошлых системах. Если наброски есть —
   берите их за основу и проверьте по чек-листу из `knowledge/04_…`, чего не хватает.
1. **Аккаунт-владелец.** Есть ли общий Google-аккаунт компании? Таблицу создаём на нём.
   Если его нет — попросить руководителя завести; до этого строим в черновике.
2. **Источники по каждому фулфилменту:** у UPSELLER и UPMARKET есть и API, и выгрузка
   файлом из кабинета. Выясни, какие именно отчёты есть (остатки, приёмки, отгрузки),
   есть ли документация к API, и попроси по одному реальному файлу каждого отчёта.
3. **Источники по каждой площадке:** есть ли API-ключи кабинетов (WB, Ozon, ЯМ, Lamoda)
   у обеих ИП, или только ручные выгрузки.
4. **Что уже есть на руках:** таблицы по ЯМ (логист пришлёт ссылки), накладные
   приходов, старые таблицы, план распределения сезона. Старые данные — справка, а не факт (см. `knowledge/03_…`).
5. **Кто будет пользоваться:** список менеджеров площадок и что каждому нужно видеть.
6. **Что горит:** какой вопрос логисту нужно закрыть первым (обычно «сколько можно
   отгрузить на площадку X»). С него и начинайте.

По итогам предложи логисту порядок подключения источников и получи согласие.

## Этап 1. Каркас

В согласованном с логистом формате соберите каркас: справочник товаров, места для
журналов движения, журнал загрузок. Заполните справочник товаров (баркод — ключ;
сверьте, что баркоды не повторяются). Сразу настройте защиту и резервное копирование
(скилл `rezerv-i-zashchita`) — до первых данных, а не после.

## Этап 2. Первый источник до конца

Яндекс Маркет уже готов: загрузите «Приёмки_МП» из `data/` (скилл `ym-priemki`),
сверьте итог с файлом. Это образец: так должен выглядеть каждый журнал — с номерами
документов, датами, сверенными итогами.

## Этап 3. Остальные источники по одному

Для каждого — скилл `podklyuchenie-istochnika`. Разумный порядок: остатки
фулфилментов (без них нельзя отвечать «сколько можно отгрузить») → отгрузки
фулфилментов → приёмки остальных площадок → приходы партий → возвраты и вывозы.

## Этап 4. План и расчёты

Перенесите план распределения текущего сезона строками в «План_распределения».
Источник — решение руководителя/логиста, а не старая таблица: в ней план подгонялся
под факт. Постройте «Остаток плана» и «Расхождения», пройдите расхождения с логистом.

## Этап 5. Витрина и заявки менеджеров

Только когда расчёты сходятся — открывайте витрину менеджерам и заводите листы заявок.

## Как принимать решения по структуре

- Любое изменение структуры — сначала описание логисту («что добавляю, зачем, что
  изменится для менеджеров»), после «да» логиста — резервная копия, затем правка.
- Не добавляйте поле «на всякий случай». Поле нужно, если по нему считают, ищут или
  сверяют.
- Формулы — простые и однотипные по всему столбцу. Сложную логику лучше считать
  скриптом и записывать результат, чем прятать в формулу на три строки.
- После каждого этапа — запись в `ЖУРНАЛ_ПРОЕКТА.md`: что сделано, какие решения
  приняты и почему, что открыто.
