# Яндекс Маркет: как устроены поставки и откуда брать факт

Работаем по модели FBY: товар лежит на складах Маркета. У каждой ИП свой кабинет и
свой API-ключ (кабинет → Настройки → API-ключи; нужен доступ к поставкам и каталогу).

## Заявки на поставку

- **Транзитная поставка** — одна родительская заявка «ВРЦ-1234567», которую фулфилмент
  везёт в одну точку (сортировочный центр или транзитный склад Софьино), а Маркет сам
  развозит по складам: Софьино, Екатеринбург, Ростов-на-Дону, Казань, Шушары, Самара.
  У родителя есть **дочерние заявки** — по одной на склад, у каждой свой номер
  (8 цифр, например `31918354`). По этому номеру заявка ищется в кабинете.
- **Прямая поставка** — формально тоже родитель + одна дочерняя заявка на один склад.
- Количество товара, план и факт есть **только у дочерних заявок**. Родитель — пустая
  обёртка.

## API (то, что использует `scripts/ym_supplies_export.py`)

- `POST /v2/campaigns/{campaignId}/supply-requests` — список заявок. Поля: `id.id`
  (внутренний номер), `id.marketplaceRequestId` (номер в кабинете), `type`, `subtype`,
  `status`, `targetLocation.name` (склад), `targetLocation.requestedDate` (плановая
  дата приёмки), `parentLink`, `counters`.
- `POST /v2/campaigns/{campaignId}/supply-requests/items` с `{"requestId": id.id}` —
  состав: `offerId` (артикул в кабинете), `counters.planCount` (заявлено),
  `factCount` (принято), `shortageCount`, `surplusCount`, `defectCount`.
- `POST /v2/businesses/{businessId}/offer-mappings` — каталог: `offerId → barcodes`.

## Что считать приёмкой

Брать заявки, где одновременно:

- `type == "SUPPLY"`;
- `subtype == "VIRTUAL_DISTRIBUTION_CENTER_CHILD"` — дочерняя заявка поставки с
  фулфилмента;
- `status == "FINISHED"` — приёмка завершена. Факт — `factCount`.

Не брать:

| Что | Почему |
|---|---|
| `subtype == "VIRTUAL_DISTRIBUTION_CENTER"` | родитель-обёртка, количеств нет |
| `subtype == "MOVEMENT_SUPPLY"` | Маркет сам перемещает товар между своими складами — это не наша отгрузка |
| `INVENTORYING_SUPPLY…` | находки инвентаризации, единицы штук |
| `status == "CANCELLED"` | заявку отменили, товар по ней не принимался |
| `type == "WITHDRAW"`, `"UTILIZATION"` | вывоз и утилизация — обратное движение, отдельный журнал |

Статусы «ещё не принято»: `ACCEPTED_BY_WAREHOUSE_SYSTEM` (создана), `SHIPPED_TO_SERVICE`
(едет), `ARRIVED_TO_SERVICE` (на складе), `WAREHOUSE_HANDLING` (идёт приёмка). Это не
факт: такие заявки ведём отдельным списком и переносим в журнал после `FINISHED`.

## Ловушки (каждая уже стоила нам ошибки)

1. **Дочерние заявки тоже имеют «детей».** У дочерней поставки в `childrenLinks` бывают
   заявки на вывоз и утилизацию непринятого товара. Отсекать родителя надо по
   `subtype`, а не по признаку «есть childrenLinks» — иначе выпадают настоящие
   поставки (так однажды недосчитали 123 шт из 551 по одной модели).
2. **Отменённое направление пересоздаётся.** Фулфилмент отгрузил по ВРЦ, Маркет отменил
   одно направление (например Ростов), товар приняли по новой заявке через пару дней.
   У фулфилмента отгрузка числится под старой ВРЦ, у Маркета приёмка — под новой.
   При сверке ищите пересозданную заявку по составу, а не объявляйте товар потерянным.
3. **Дата в API — плановая дата приёмки**, не дата отгрузки с фулфилмента. Для транзита
   это дата на конечном складе, она на 3–10 дней позже отгрузки. Дату отгрузки знает
   только фулфилмент.
4. **Приёмка может идти неделями.** Заявка в `WAREHOUSE_HANDLING` две-три недели —
   повод написать в поддержку, но не повод вносить план как факт.
5. **Удалённые карточки.** Если товар удалён из каталога, баркод по `offerId` уже не
   получить. Такие строки помечаются, баркод берётся из справочника товаров по артикулу
   и размеру, запись вносится в `data/barcode_overrides.csv` с пометкой «проверить».
6. **Лимиты.** Список заявок и составы отдаются медленно: полная выгрузка двух
   кабинетов — около 25 минут. Скрипт хранит кэш и при повторном запуске перечитывает
   только изменившиеся заявки.
7. **Недостача — не всегда потеря.** Часть «недостачи» потом находится и принимается
   инвентаризацией или уезжает в заявки на вывоз непринятого товара. Это отдельные
   движения, в журнал приёмок их не подмешиваем.
